# 新后端性能基线（NestJS + MySQL 8 + Redis）

> 目标：给出可复现的延迟/吞吐基线，暴露并修掉可量化的工程缺陷，而不是追求好看的数字。
> 复现命令：`npm run nest:bench`（自动起停 MySQL 3307 / Redis 6380 / NestJS 4300、重建库并灌种子数据）

## 1. 方法与口径

| 项 | 口径 |
| --- | --- |
| 压测脚本 | `tools/bench-nest.mjs`，门禁包装 `tools/gate-bench.mjs` |
| 样本 | 每个接口 **500 次**请求，固定并发 **20**（`BENCH_TOTAL` / `BENCH_CONC` 可调） |
| 指标 | p50 / p95 / p99 / max 延迟（含 HTTP 往返与服务端处理）、QPS、错误数 |
| 数据 | 每次运行由 `db/seed-min.mjs` 重建（12 用户 / 4 教员档案 / 3 业务员 / 2 代理 / 演示订单），规模一致 |
| 环境 | 单机 Windows、便携 MySQL 8.4（3307）、Redis 5（6380）、Node 22.14、NestJS 单进程 |
| 说明 | 两轮独立运行取稳定值；单轮波动约 ±10%，低于 200 次采样时噪声会显著变大（首轮 200 次时同一接口曾出现 2–6 倍抖动） |

## 3. 写路径（抢单临界区）

| 场景 | QPS | p50 | p95 | 正确性 |
| --- | --- | --- | --- | --- |
| `POST /demands/:id/apply`：**同一需求** 50 个并发抢单 | 64~67 | ~400ms | ~700ms | 成功 1 次、被拒 49 次（唯一索引 + Redis 锁双保险） |

结论：
- 写路径的秒级延迟来自**同一临界区的锁自旋**（`common/lock.ts`：SET NX PX + 指数退避，自旋上限 2s）。50 个请求抢同一行，只有 1 个能拿到锁，其余按退避等待后由唯一索引拒绝——这是"宁可慢也不能错"的取舍，正确性优先。
- 不同需求之间互不阻塞（锁 key 带 `demand_id`），因此真实业务（多需求并发抢单）不会出现该延迟；`concurrency-mysql.mjs` 覆盖了「100 个不同教员抢同一需求」的隔离性。

## 4. 本轮据此修复的性能缺陷

| # | 缺陷 | 修复 | 效果 |
| --- | --- | --- | --- |
| 1 | `parent.home` 首页聚合把 10 次互不依赖的取数**串行** await（区域/横幅/公告/教员/地址/优惠券/进行中订单/未读/规则×2/信用分） | 改为 `Promise.all` 并发取数（MySQL 连接池 40 足以承载） | 单请求 DB 往返从 11 次串行降为 1 批次；`/parent/home` p95 从 65.9ms 降到 **39.9~41.4ms**（-40%） |
| 2 | `nearbyForTeacher` 在 for 循环里逐条查 `applications`（N+1：需求数 × 1 次查询） | 先取该教员对这批需求的报名状态（`IN (?,?,…)` 单查询 + Map 命中），循环内只做内存判断 | 查询数由 `1 + N` 降为 **2**；`/teacher/nearby-demands` 在 500 次采样下 p95 稳定 **17ms**、QPS 1323+（需求表越大收益越明显） |

## 5. 已知性能边界与后续建议

1. **教员广场是全表扫描 + 内存排序**：`/parent/teachers` 会把审批通过的教员全部取出、在应用层算距离/优先级再排序分页（距离与派单权重是业务规则，无法直接下推 SQL）。
   当前 p99 ≈ 95ms（长尾来自全表扫 + 排序）。教员规模上万时建议：① 用 `base_lat/base_lng` 建 `SPATIAL` 索引或加经纬度边界框预筛；② 优先级用物化列（写入时算好）+ 复合索引排序。
   **注意**：任何优化都必须同时保留「电子围栏 + 六维筛选 + 派单权重」的语义，`rules.test.js` 会对排序优先级做断言。
2. **后台财务总览是多表聚合**（订单/钱包/提现/发票/担保台账/奖励/对账）：体积随订单线性增长，建议生产上按日聚合成 `finance_daily` 物化表，接口只读聚合表 + 当日增量。
3. **写接口锁自旋**：同一热点（抢单、结算）高并发时 p95 会到百毫秒级。若业务要更高吞吐，可改为「先入队 + 异步处理」（Redis Stream），HTTP 层只做受理，不代表要牺牲正确性。
4. **单进程实测**：以上为单 NestJS 实例；水平扩容后 Redis 锁与 MySQL 行锁仍是全局约束，瓶颈会转向 MySQL 写入。
5. 压测未覆盖：长连接/WebSocket（未使用）、大文件上传（证书图片走 URL 字段）、CDN 静态资源（当前由 NestJS 托管，生产建议前置 Nginx）。
